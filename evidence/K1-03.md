# Работа K1-03

- Код студента: Соня
- Что сделано: подтверждён отказ API, сопоставлены ответы web и логи, затем API восстановлен и создана новая заявка.

## Команды

```text
docker compose stop api
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/api/requests
docker compose ps -a
docker compose logs --tail=20 web
docker compose start api
docker compose ps
```

Для проверки заявок использовались HTTP-запросы к `web` на `http://127.0.0.1:8080/api/requests`.

## Наблюдения

До остановки API была создана заявка №1 с видом `screen`.

После `docker compose stop api`:

- `http://127.0.0.1:8080/health` вернул `200 OK` и `{"process": "running", "role": "web"}`.
- `http://127.0.0.1:8080/api/requests` вернул `503 Service Unavailable` и `{"error": "upstream_unavailable", ...}`.
- `docker compose ps -a` показала у `api` статус `Exited (137)`, при этом `web` оставался `healthy`.
- В журнале `web` есть событие `upstream_unavailable` с адресом `http://api:8000` и строка запроса `/api/requests` со статусом `503`.

После `docker compose start api` контейнер API снова стал `healthy`. Запрос списка заявок вернул ранее созданную заявку №1. Затем была создана заявка №2 с видом `software`; итоговый список содержал обе заявки.

## Причина и восстановление

Web-сервис продолжал работать, но при остановленном API не мог передать ему запрос списка заявок по адресу `http://api:8000`. Поэтому web возвращал пользователю 503. Запуск `docker compose start api` восстановил зависимый сервис, после чего список и создание заявок снова стали доступны.

## Ответ на вопрос из задания

`health` у web остался успешным, потому что он проверяет сам процесс web. Эта проверка не подтверждает доступность API, к которому web обращается только при работе со списком и создании заявок.
